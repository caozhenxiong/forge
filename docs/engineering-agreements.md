# 工程约定

> 说明：这份文档只维护协作与工程约定。当前代码与业务状态总览请优先看 `docs/current-state.md`，文档入口请看 `docs/README.md`。

## 目的

这份文档把 `Forge` 的工程约定持久化下来，避免后续继续在错误思路上修修补补。

它关注的不是某一个具体 bug，而是：

- 如何判断当前方向是不是错了
- 如何避免把局部修补继续堆成更大的冗余
- 如何在演进中保持优雅性、可复用性、可扩展性和可维护性

根目录的 `AGENTS.md` 是高优先级短约定；本文档是完整说明。

## 一、判断顺序

后续每次动手前，先按下面顺序判断：

1. 当前问题是不是整体思路错误
2. 当前问题是不是职责边界错误
3. 当前问题是不是抽象层级错误
4. 只有在以上三项都没有问题时，才进入具体 bug 修复

这意味着：

- 如果发现整文件往返生成本身就是错误思路，就不应继续在整文件生成链上补丁
- 如果发现一个类已经承担规划、生成、校验、落盘、恢复、评审等过多职责，就应该先拆边界
- 如果发现 prompt 在解决具体场景，而不是解决一类问题，就应该先改 prompt 设计方法

## 二、优先级

工程优先级按以下顺序执行：

1. 正确的整体思路
2. 清晰的职责边界
3. 通用且稳定的抽象
4. 优雅性
5. 可复用性
6. 可扩展性
7. 具体功能修复

如果前 3 项有问题，不应直接跳到第 7 项。

## 三、去硬编码原则

### 1. 不做场景特判

避免这样的规则：

- 某个项目必须这样拆
- 某个页面必须单文件
- 某个案例必须先做某个按钮

应该改成：

- 信息来源规则
- 约束升级规则
- 结构完整性规则
- 阶段职责边界规则
- 验收信号规则

### 2. 解决一类问题

后续所有修复都要回答：

- 我修的是这个案例，还是这一类问题？

只有“这一类问题”的修复才允许进入主链。

### 3. 先做 build-vs-buy 判断

如果某项能力明显属于：

- 工具链能力
- 解析能力
- 编辑器能力
- 代码生成辅助能力
- 结构化处理能力

并且实现复杂、容易演化成底层轮子时，必须先判断：

- 是否已有成熟类库
- 是否已有现成工具
- 是否已有可复用框架
- 是否已有仓库内可扩展的现成抽象

优先顺序应为：

1. 现成成熟方案
2. 在现成方案上做薄适配
3. 自研最小补充层
4. 最后才是完整自研

不允许一上来就手搓复杂底层能力。

### 4. Prompt 不针对案例写规则

Prompt 的职责是：

- 管理来源
- 管理权重
- 管理约束等级
- 管理阶段职责

Prompt 不应用来堆：

- 当前页面怎么做
- 当前项目怎么拆
- 当前 bug 的关键词黑名单

### 5. 不用 regex 猜模型语义

对 agent / reviewer / planner / tester 这类大模型输出：

- 不要依赖正则或关键词匹配去猜语义
- 不要把“模型大概率会这么说”当成稳定协议
- 不要用中文/英文关键词黑名单去判断高层语义

应该改成：

- 模型输出结构化字段
- 确定性层只解析固定协议
- policy/gate 基于结构化字段裁决

允许保留的 regex 只限于：

- 我们自己定义的固定协议/marker
- 文档结构标题
- metadata / schema / 固定格式解析

不允许保留的 regex 语义层包括：

- 低权重内容判断
- 开放问题判断
- 性能结论判断
- 建议/设计选择/推断等语义归类
- reviewer prose 的意图识别

补充硬约束：

- 不允许基于自然语言 regex/关键词匹配直接驱动流程跳转、gate 结论或失败分类
- 只有“固定协议/固定结构”的解析才允许保留 regex
- 如果某段逻辑依赖大模型返回的高层语义，必须先把语义移到结构化字段里，再由确定性 policy 消费

### 6. 不引入魔法数字和魔法字符串

后续流程重构里，默认禁止继续把以下内容散落硬写在代码里：

- 协议 key
- metadata key
- artifact key
- marker/tag
- reason code
- 阶段名
- 重试次数
- 预算阈值
- 默认时间/长度限制

这些内容应尽量收敛到：

- 常量类
- spec 对象
- policy 对象
- 配置对象

原则：

- 稳定协议字段要集中定义，不要在多个类里手工拼字符串
- 可调阈值优先配置化，不要把“3 次重试 / 2200 token / 500ms”这类数字直接埋在流程代码里
- 如果某个值需要被多个模块共享，它就不应继续停留在局部字面量中
- 只有一次性、无复用价值、且不会影响协议/流程语义的局部值，才允许保留为局部字面量
- 对外协议动作、测试 action、stage action、artifact block kind、runtime metric key 这类稳定值，优先使用 enum/spec，而不是反复写字符串
- 每轮清理之后必须再次全局复扫；只要还存在新的 prose 语义猜测、散落 key 或阈值字面量，就继续收口，不能把“剩下一点”当成可接受状态

### 7. 禁止过渡实现进入主链

不允许以以下理由把明知有问题的实现带入主链：

- 先让链路跑起来
- 先保留一层过渡兼容
- 先临时兜底，后面再清理
- 先做半套，剩下以后再收

如果当前方案需要依赖这些前提才能成立，说明：

- 抽象还不对
- 边界还没收清
- 主链还不应该落代码

这类情况下，正确动作是：

- 先改方案
- 先补缺失抽象
- 先把新旧边界彻底切开

不允许：

- 把“过渡实现”长期留在主代码路径
- 把明知会回头删除的兼容层直接接进核心执行链
- 让新旧两套主路径长期并存，只靠注释或 TODO 提醒后续清理

补充硬约束：

- 任何“为了降低风险而暂时保留”的逻辑，都视为未完成，而不是稳妥
- 只要主链还依赖这类暂时保留逻辑，本次任务就不得宣称完成，也不得进入下一阶段
- 不允许用“先保留一层，后面再删”来换取当前任务通过

### 8. 禁止为了打通链路而引入临时硬编码

不允许为了“先跑通当前案例”而引入以下内容：

- 场景特判
- 项目特判
- 关键词黑名单/白名单
- 临时预算上限
- 临时重试阈值
- 临时 fallback 路由
- 临时协议 key / marker / reason code

如果某次改动只能靠这类临时硬编码推进，必须先停下来判断：

1. 缺的是不是结构化 contract
2. 缺的是不是 policy/config/spec
3. 缺的是不是更小的稳定抽象
4. 缺的是不是工具层/验证层能力

只有把这些正式来源补齐后，才允许继续推进主链实现。

硬约束：

- 不允许把“后面再删”当成引入临时硬编码的理由
- 不允许把过渡阈值或场景字面量直接放入核心类
- 不允许为了单次集成测试通过而污染长期主链
- 任何“后续再清理”的说法，都视为本次任务失败，而不是计划安排
- 如果某类问题必须留到后续任务再清，说明当前任务没有真正收口，必须继续在当前任务内完成

## 三点八、任务失败判定

以下两条不再只是过程提醒，而是直接的任务成败判定：

- 任何“为了降低风险而暂时保留”的逻辑，都视为未完成，而不是稳妥。
- 任何“后续再清理”的说法，都视为这次任务失败。

只要出现以上任一情况：

- 不得宣称当前任务已完成
- 不得进入下一阶段
- 不得提交半成品实现充当收口结果

## 三点五、方案讨论约定

### 1. 不机械顺着用户方案执行

当用户主动提出一个方案、路径或架构判断时，后续实现者必须先判断：

- 这个方案是不是整体上正确
- 有没有更稳、更小、更优雅的替代方案
- 当前方案是否会继续放大已有的错误抽象

如果判断存在更好的方案，必须：

- 明确指出原方案的问题
- 给出替代方案
- 解释为什么替代方案更优

不允许：

- 明知方案较差却只是为了“顺着做”而继续执行
- 用沉默默认认可一个会把系统继续带偏的方案

### 2. 反驳要基于工程理由

反驳用户方案时，必须基于：

- 整体思路是否正确
- 职责边界是否清晰
- 抽象是否通用
- 是否会继续引入硬编码
- 是否更优雅、更易维护、更可扩展

不允许用“感觉不好”这种模糊理由直接否定。

## 四、注释约定

### 1. 注释语言

- 代码注释默认使用中文

### 2. 必须补注释的地方

- 流程边界
- 阶段 gate
- 恢复链
- 契约判定
- 复杂策略切换
- 明确“不负责什么”的类和方法

### 3. 注释的目标

注释要解释：

- 为什么这样设计
- 边界在哪里
- 这段逻辑解决哪一类问题
- 为什么不用更直观的写法

不要写：

- 给变量赋值
- 调用了某个方法
- 明显从代码就能看出来的动作

## 五、架构演进约定

### 1. 先收口，再扩展

当工作流没有跑通黄金路径时：

- 优先稳定化
- 优先降低冗余
- 优先修正错误抽象

不要继续叠加：

- 新角色
- 新 prompt 规则
- 新流程分支
- 新上下文层

### 2. 大类必须拆边界

如果某个类开始同时承担：

- 规划
- 生成
- 校验
- 恢复
- 渲染
- 阶段完成判定

就说明边界已经错了，应该拆。

### 3. 生成策略优先小块化

后续生成链优先遵循：

- 任务拆分
- 边界拆分
- 小块生成
- 本地组装
- 本地校验

整文件 round-trip 只能作为最后 fallback，而不是默认主路径。

### 4. 逻辑变更必须同步更新文档

任何会改变系统行为、流程语义、协议格式、状态落盘、review/test 规则的代码改动，都必须同步更新对应文档。

至少要检查：

- `README.md`
- `docs/workflow-rules.md`
- `docs/redesign-roadmap.md`
- `docs/current-state.md`
- 相关当前策略文档，例如：
  - `docs/editing-strategy.md`
  - `docs/README.md`

原则：

- 不允许“代码已经变了，文档以后再补”
- 不允许让设计文档长期描述一个已经不存在的主路径
- 不允许让运行规则文档与真实 gate 行为分叉

## 六、流程约定

### 1. coder 必须真正实现

- 骨架不是完成
- 占位不是完成
- 空函数不是完成
- 半成品不是完成

### 2. review 不能假通过

只要还存在阻塞性的能力缺口，就不能 `APPROVED`。

### 3. test 不能只测表面

测试要验证：

- 真实行为
- 真实状态变化
- 真实交付契约

不是只验证：

- 页面能打开
- 按钮能点
- 没报错

### 4. 文档不能发明硬约束

文档阶段要区分：

- 用户要求
- 上游事实
- 推断
- 设计选择
- 建议
- 待确认问题

不能把低确定性内容升级成硬约束。

## 七、每次改动前的自检清单

- 当前问题是不是整体思路错误？
- 当前问题是不是职责边界错误？
- 这次改动有没有新的场景特判？
- 这次改动是不是在解决一类问题？
- 这项复杂能力是否已经有合适的类库、工具或现成抽象可复用？
- 用户当前提出的方案是否存在更优替代？如果有，是否已经明确提出反驳和替代方案？
- 结构是否比之前更优雅？
- 是否补了必要的中文注释？
- 这次逻辑变更对应的文档是否已经同步更新？
- 是否降低了耦合和冗余？
- 是否让未来扩展更容易，而不是更难？
- 是否又在用 regex/关键词匹配去猜模型自由文本的语义？如果是，是否能改成结构化输出 + 确定性 policy？

## 八、黄金路径要求

在黄金路径没有真实跑通前：

- 不接受表面通过
- 不接受假完成
- 不接受假 review
- 不接受假 test

当前黄金路径是：

- 俄罗斯方块集成测试

后续所有改动，都要优先服务于把这条链真实跑通。
